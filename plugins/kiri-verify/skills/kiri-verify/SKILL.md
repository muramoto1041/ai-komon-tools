# 桐 一括処理ファイルの検証

桐の一括処理（cmx）・イベント処理（kex）のテキストを、ヘルプの書式と照合し、本文のロジックも読んで問題を報告する。
目的は**ヘルプを根拠にした指摘**。推測で「たぶん正しい」「たぶん誤り」と言わず、ヘルプに書いてあること・書いていないことを分けて伝える。

## 前提

- ファイルは **Shift-JIS**。UTF-8 で保存し直すと桐が読めなくなる。検証は読むだけにし、修正を頼まれていなければファイルは書き換えない。
- `.txt` を直しても、**桐に取り込み直すまで動作には反映されない**。修正を提案したら、報告の最後に必ず添える。
- フォルダに CLAUDE.md があれば先に読む。顧客ごとのファイル名の規則や注意が書いてある。
- 対象のファイルは本番で動いていることが多い。「ヘルプに記載がない書き方」は、古い書式として桐が受け付けている可能性がある。「誤り」とは区別して書く。

## 手順

### 1. 走査スクリプトで全体をつかむ

```bash
python -I <このスキルのフォルダ>/scripts/kiri_scan.py <対象フォルダ>/*.txt
```

- 走査結果には、次のものが出る。
  - ファイルごとの使用コマンド（回数・行・ヘルプのページ名）
  - 機械チェックの候補
  - 定義が見つからない手続き呼び出し
  - 照合するヘルプページの URL 一覧
- `ライブラリ` で読み込むファイル（例：`共通処理_cmx.txt`）も一緒に渡す。渡さないと、ライブラリにある手続きまで「未定義」と判定される。
- 「候補」は機械的な判定にすぎない。必ず本文とヘルプで確かめてから報告に載せる。
- 「対応表にないコマンド」が出たら、綴りの誤りか、対応表に足りないコマンドのどちらか。後者なら `references/command-pages.md` に追記する。

### 2. 本文をすべて読む

```bash
python -I <このスキルのフォルダ>/scripts/kiri_scan.py --dump <ファイル>
```

行番号付きの UTF-8 で表示される。ロジックの不具合はスクリプトでは見つからないので、全行に目を通す。
長いファイルは、出力を保存してから分けて読む。

### 3. ヘルプと照合する

- まず `references/verified-notes.md` を読む。確認済みのコマンドなら、ページを読み直さなくてよい。
- それ以外は、ヘルプの本文を取得する：`https://www.kthree.co.jp/kihelp/cmd/stx/<page>.html`。
  - `index.html?page=…` の形では本文が取れない。
  - ページ名は走査結果か `references/command-pages.md` で調べる。
  - 複数のページはまとめて並行して取得する。
- 取得するときは「書式（構文）・パラメータ・終了状態の値・注意事項を正確に抜き出して」と頼む。要約の過程で言い換えられることがあるので、指摘の根拠にする部分は原文の表現を確かめる。
- 関数（`#曜日`、`#対応文字列` など）は別のヘルプにある（`kihelp/fnc/…`、カテゴリは `command-pages.md` の末尾）。疑わしいものだけ調べ、調べなかったら「確認していない範囲」に書く。
- 新しくわかった書式は、`references/verified-notes.md` に追記しておく。次回からページを読み直さずに済む。

### 4. ロジックを確認する

`references/checklist.md` に沿って確認する。次の点は、実際の顧客ファイルで見つかった問題。
- 表の開閉件数の食い違い
- 「0 = 全部」のような特別な値が偶然渡されるケース
- 到達しない分岐
- 配列の添字の範囲外
- 定義されていない手続きの呼び出し

### 5. 報告する

## 報告の形式

ターミナルへの返答として、次の順に書く。該当がない節は省く。場所は `[ファイル名:行](ファイル名#L行)` のリンクにする。

```
（冒頭1〜2文：何ファイルを、どのヘルプと照合したか。ファイルは変更していないこと）

## 1. 直すべき箇所
| # | 場所 | 問題 | 直し方 |
（ヘルプの書式に反するもの、明らかな不具合。直し方は具体的なコードで）

## 2. ヘルプに載っていない書き方（今動いているなら急がなくてよい）
（記載外の書式・表記ゆれ。正式な書き方を添える）

## 3. 使われないコード・未定義
（到達しない分岐、定義が見つからない手続き、未宣言の変数、型の合わない代入）

## 4. エラーに強くするための任意の改善
（終了状態がない、など）

## ヘルプどおりで問題なかったもの
（確認したコマンドを1段落で並べる。どこまで確認したかが伝わるように）

## 確認していない範囲
（関数、ほかのファイルで宣言されているとみられる変数、など）

（修正したら桐へ取り込み直しが必要、のひと言）
参照したヘルプ：[ページ名](URL)、…
```

報告で守ること：
- **重要度の順に分ける。** 「直すべき」に記載外の書式まで混ぜると、本当に危ない箇所が埋もれる。
- **根拠を書く。** 「ヘルプの書式は `手続き実行 (<条件式>)，<手続き名>()`」のように、ヘルプの書式を引用する。
- **言い切れないことは、言い切らない。** 例：「`ErrHandler` はこのファイル群では未定義（ほかのライブラリにある可能性あり）」。

## 同梱ファイル

- `scripts/kiri_scan.py`：走査と機械チェック（`--dump` で行番号付き表示）。
- `references/command-pages.md`：コマンドとヘルプページ名の対応表。スクリプトもこの表を読むので、列の形式を保って追記する。
- `references/verified-notes.md`：ヘルプで確認済みの書式メモ。
- `references/checklist.md`：検証の観点と、実例。
